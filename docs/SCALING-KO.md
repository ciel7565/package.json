# 많은 사람이 한꺼번에 들어올 때 — 수용 인원과 증설 안내서

전통발효체험관 메타버스 서버가 **몇 명까지 버티는지**, 더 많은 사람을 받으려면 **무엇을 어떤 순서로 바꾸면 되는지**를 적은 문서예요.
8단계(CONTRACT §16.9)에서 만든 것과, 그것을 실제로 돌려서 **잰 숫자**를 함께 담았어요.

> **이 문서를 읽는 법**
> - **〔잼〕** 표시는 이 문서를 쓰면서 시험 서버에서 직접 돌려서 얻은 숫자예요.
> - **〔어림〕** 표시는 잰 숫자로 계산한 추정값이에요. 실제와 다를 수 있어요.
> - **〔못 잼〕** 표시는 이 시험 환경에서는 확인하지 못한 것이에요 (Windows · XAMPP · PHP 7.2 · 실제 인터넷 회선 등).
> - 잰 적이 없는 숫자를 "된다"고 약속하지 않아요. 큰 행사 전에는 9장의 방법으로 직접 확인해 주세요.

## 1. 한눈에 보기

| 목표 | 필요한 것 | 근거 |
|---|---|---|
| **이 PC 한 대 (XAMPP 그대로)** — 동시 접속 **약 300명** | 설정 3가지만 확인 (5장): Apache 스레드 수, opcache 켜기, MariaDB 메모리. 기본값 `max_online = 300` 그대로 | 〔잼〕 시험 서버(4코어 중 1코어도 못 쓰는 상태)에서 500명 · 1,000명이 오류 0번으로 돌았어요. 〔못 잼〕 Windows · PHP 7.2 는 직접 재지 못해서, 잰 값의 3분의 1 이하인 300명을 기본 정원으로 잡았어요. **opcache 를 켰을 때**의 숫자예요 (끄면 100~150명) |
| **1,000명** | 같은 PC 또는 4~8코어 서버 한 대 + opcache · 설정 조정 (6장) | 〔잼〕 시험 서버에서 1,000명: 오류 0번, sync p50 4.8 ms · p95 201 ms. 다만 서버가 호출 간격을 2배쯤 늘린 상태였어요. 간격을 늘리지 않으려면 8코어 〔어림〕 |
| **10,000명** | 리눅스 서버 한 대(16코어 이상) + nginx + php-fpm + APCu + CDN (7장) | 〔어림〕 잰 CPU 사용량으로 계산. 1만 명을 실제로 돌려 보지는 못했어요 |

300명을 넘는 사람이 오면 서버가 느려지는 대신 **대기실**이 열려요. 먼저 온 순서대로 "앞에 N명"을 보여 주고, 자리가 나면 자동으로 들어가요. 이미 들어와 있는 사람은 쫓겨나지 않아요.

## 2. 낱말 풀이

| 낱말 | 뜻 |
|---|---|
| 동시 접속 | 같은 순간에 체험관 안에 들어와 있는 사람 수. 하루 방문자 수와는 달라요 (하루 3,000명이 와도 동시에는 200명일 수 있어요). |
| 요청 | 브라우저가 서버에 한 번 물어보는 것. 체험관 화면은 1~4초마다 한 번씩 "내 위치는 여기, 주변 사람은?" 하고 물어봐요. |
| 초당 요청 (rps) | 서버가 1초에 받는 요청 수. 300명이 평균 2초에 한 번 물으면 초당 150번이에요. |
| CPU 코어 | 컴퓨터가 동시에 계산할 수 있는 일꾼 수. "4코어"면 네 가지 일을 동시에 해요. |
| 일꾼 (스레드 · 프로세스) | 웹 서버(Apache)가 요청을 처리하려고 준비해 둔 손. XAMPP 의 Apache 는 보통 150개를 준비해요. |
| 연결 유지 (keep-alive) | 브라우저와 서버가 한 번 연 통로를 잠깐 열어 두는 것. Apache 는 열린 통로 하나마다 일꾼 하나를 붙잡아 둬요. |
| SQL 문 | 서버가 데이터베이스(MariaDB)에 하는 질문 하나. 적을수록 빨라요. |
| 캐시 | 자주 쓰는 답을 잠깐 기억해 두는 곳. 이 서버는 `data/cache` 폴더의 작은 파일(기본) 또는 메모리(APCu)를 써요. |
| opcache | PHP 가 프로그램 파일을 매번 다시 읽고 해석하지 않도록 기억해 두는 기능. PHP 에 들어 있지만 XAMPP 에서는 보통 꺼져 있어요. |
| APCu | PHP 가 쓰는 메모리 캐시(추가 확장). 파일 캐시보다 조금 빨라요. 없어도 돼요. |
| 채널 | 서로 보이는 체험객 묶음. 한 채널에 60명이 차면 새 채널이 열려요. 같은 채널 안에서도 가까이(90 m 안, 같은 장소) 있는 사람만 화면에 그려요. |
| 대기실 · 대기표 | 자리가 꽉 찼을 때 줄을 서는 곳과 줄 번호. 번호는 서버가 서명해서 위조할 수 없어요. |
| 줄이기 (shedding) | 서버가 감당 못 할 만큼 바쁠 때, 새로 오는 사람에게 "잠시 후 다시"라고 답하고 이미 들어온 사람을 지키는 것. |
| gzip · brotli | 글자로 된 파일을 작게 줄여 보내는 방법. 브라우저가 받아서 다시 풀어요. |
| CDN | 전 세계 여러 곳에 파일 복사본을 두고 대신 나눠 주는 서비스. 체험관 화면 파일(약 6 MB)을 서버 대신 보내 줘요. |
| nginx · php-fpm | 리눅스에서 많이 쓰는 웹 서버와 PHP 실행기. 열린 통로가 수천 개여도 일꾼을 붙잡지 않아서 많은 사람에게 유리해요. |
| 프록시 | 방문자와 서버 사이에 서서 요청을 대신 전해 주는 서버 (nginx · CDN 이 그 역할을 해요). |
| p50 · p95 · p99 | 응답 시간을 빠른 순으로 줄 세웠을 때 가운데(50%), 95%, 99% 자리의 값. p95 가 100 ms 면 "100번 중 95번은 0.1초 안에 답했다"는 뜻이에요. |
| ms | 밀리초. 1,000분의 1초예요. |

## 3. 8단계에서 무엇이 달라졌나

7단계까지는 화면이 1~2초마다 "위치 알림"을, 3초마다 "채팅 확인"을 따로 물었고, 물을 때마다 서버가 데이터베이스에 9~10번씩 질문했어요. 100명이면 초당 1,000번이 넘는 질문이에요.

8단계에서는 이렇게 바꿨어요.

1. **한꺼번에 주고받기 (`api/sync.php`)** — 위치 · 주변 사람 · 채팅 · 공지 · 접속자 수를 요청 한 번에. 서버가 "다음에는 몇 초 뒤에 물어봐"(`n`)라고 정해 줘요: 여럿이 움직일 때 1~1.5초, 혼자 움직일 때 2.5초, 가만히 있을 때 4초, 탭이 가려져 있을 때 20초. 서버가 바쁘면 이 간격을 자동으로 늘려요.
2. **데이터베이스를 거치지 않는 지름길** — 처음 한 번만 로그인을 확인하고 5분짜리 서명된 통행증(토큰)을 줘요. 그 뒤의 호출은 통행증과 캐시만 봐요. **SQL 0문**이에요. 로그아웃 · 정지 · 권한 변경 · 비밀번호 변경은 그 즉시 통행증을 무효로 만들어요 (시험으로 확인).
3. **채널과 관심 영역** — 60명씩 묶고, 그 안에서도 가까운 40명까지만 보내요. 바뀐 것이 없는 사람은 번호만 보내요.
4. **수용 인원 관리와 대기실 (`lib/Gate.php`, `api/queue.php`)** — 정원(`max_online`)이 차면 대기표를 주고, 로그인은 1초에 5번까지만 처리해요(비밀번호 확인 한 번이 CPU 를 0.25초쯤 써서, 한꺼번에 몰리면 서버가 멈추기 때문이에요).
5. **저장 줄이기** — 바뀐 것이 없으면 저장하지 않고, 같은 내용이 다시 오면 서버가 검사 · 기록 없이 "그대로예요"라고만 답해요.
6. **화면 파일 미리 압축** — 약 6 MB 인 `index.html` 옆에 미리 줄여 둔 복사본을 두고, 브라우저가 받을 수 있으면 그것을 보내요.
7. **연결 바로 돌려주기** — 다음 호출이 1초 이상 뒤이면 응답 뒤에 통로를 닫아서 Apache 의 일꾼을 바로 돌려줘요.

### 3.1 요청 한 번의 비용 — 전과 후 〔잼〕

Apache 2.4 + mod_php(PHP 8.3) · opcache 켬 · SQLite · 한 사람이 30번씩 불러 평균 (`tools/loadtest.mjs --probe`).

| 요청 | 7단계: SQL 문 | 8단계: SQL 문 | 8단계: 서버 처리 시간 |
|---|---:|---:|---:|
| `ping.php` (화면을 열 때 1번) | 7.1 | **0** | (처음 1번) |
| `auth/me.php` (로그인 뒤 1번) | 8.0 | **2.0** | 약 6 ms |
| `player/get.php` (로그인 뒤 1번) | 10.1 | **3.0** | 약 5 ms |
| `ranking/top.php` | 10.0 | **0.13** (60초에 한 번만 계산) | 약 1.4 ms |
| `chat/list.php` (옛 화면이 3초마다) | 10.1 | **0.1** | 약 1.5 ms |
| `presence/update.php` (옛 화면이 1~2초마다) | 9.1 | **0.03~0.07** | 약 1.5 ms |
| `sync.php` — 통행증이 있는 보통 호출 | (없던 것) | **0.00~0.03** | 약 1.5~2 ms |
| `player/save.php` — 내용이 바뀐 저장 | 약 12 | **약 10** | 크기에 따라 11~72 ms (3.2) |
| `player/save.php` — 바뀐 것 없는 저장 | 약 12 | **2** | 약 3 ms |
| `auth/login.php` | 16 | 14 | 약 250 ms (비밀번호 확인) |

- "0.03"처럼 0 이 아닌 까닭: 15초에 한 번 "차단된 주소 목록"을 데이터베이스에서 다시 읽어요. 서버 전체에서 15초에 SQL 1문이에요.
- 옛 화면(7단계 방식)도 그대로 동작해요. 옛 주소(`presence/update.php`, `chat/list.php`)도 같은 캐시에서 답하므로 옛 화면과 새 화면이 서로 보여요.

### 3.2 저장 한 번의 비용 〔잼〕

| 저장 크기 | 내용이 바뀐 저장 | 바뀐 것 없는 저장 |
|---:|---:|---:|
| 20 KB | 약 11 ms | 약 3 ms |
| 100 KB | 약 25 ms | 약 3 ms |
| 400 KB | 약 72 ms | 약 8 ms |

- 내용이 바뀐 저장은 "기본 8 ms + 1 KB 마다 0.16 ms" 정도예요. 그중 3분의 2는 전송 오류를 잡는 검사값 계산(1 KB 에 0.12 ms)이에요.
- 그래서 화면은 **바뀐 것이 있을 때만** 저장하고, 서버가 알려 주는 간격(`saveEvery`, 기본 60초, 서버가 바쁘면 더 길게)을 지켜요.
- 새 계정의 첫 저장은 SQL 약 27문(텃밭 기록을 처음 만들어요), 그다음부터는 약 10문이에요.

### 3.3 화면 파일 크기 〔잼〕

| | 크기 | 원본 대비 |
|---|---:|---:|
| `index.html` (배포용 빌드) | 6.03 MB | 100% |
| `index.gz.html` (gzip) | 1.77 MB | 29% |
| `index.br.html` (brotli, https 에서만 쓰여요) | 1.31 MB | 22% |

- `node tools/build.mjs` 가 세 파일을 함께 만들어요. `.htaccess` 가 브라우저에 맞는 것을 골라 보내요 (Apache 의 `mod_rewrite` 와 `mod_headers` 가 있을 때. 없으면 원본을 보내요).
- 두 번째 방문부터는 "바뀌지 않았어요"(304)만 주고받아서 파일을 다시 받지 않아요.
- **`index.html` 을 손으로 바꿨다면** 옆의 `index.gz.html` · `index.br.html` 을 지우거나 다시 빌드하세요. 지우지 않아도 서버가 한 시간에 한 번 확인해서, 원본과 맞지 않는 복사본은 스스로 지워요 (`data/page.json` 과 비교).

### 3.4 Apache 의 일꾼과 열린 연결 〔잼〕

Apache(mod_php)는 **열린 연결 하나마다 일꾼 하나**를 붙잡아 둬요. 방문자가 4초에 한 번 물어도, 연결을 5초 동안 열어 두면(`KeepAliveTimeout 5`, XAMPP 기본값) 그 사람은 일꾼 하나를 계속 차지해요.

| 시험 | 방문자 300명 · 일꾼 50개 | 결과 |
|---|---|---|
| 연결을 열어 둘 때 | 106명만 들어옴, 나머지는 30초 기다리다 실패 (연결 오류 337번) | 서버 CPU 는 0.2코어만 쓰고 있었어요. 일꾼이 모자랐을 뿐이에요 |
| 응답 뒤 연결을 닫을 때 (8단계 기본) | 300명 모두 들어옴, 연결 오류 0번 | 일꾼은 답하는 동안만 바빠요 |

일꾼 150개 · 방문자 400명으로도 같은 일이 일어났어요 (열어 둘 때 305명만 들어오고 첫 요청이 29초 걸림).
그래서 8단계는 다음 호출이 1초 이상 뒤인 응답(`sync`, 대기실, 저장, 채팅 보내기)에 "연결을 닫아 주세요"(`Connection: close`)를 붙여요. 설정 이름은 `capacity.close_after_ms` (기본 1000, 0 = 끄기)예요. nginx 나 CDN 뒤에서는 이 표시가 아무 영향이 없어요 (그쪽은 열린 연결이 일꾼을 붙잡지 않아요).

## 4. 부하 시험 — 어떻게 쟀나

### 4.1 시험 도구

`tools/loadtest.mjs` 가 가상 방문자를 만들어요. 가상 방문자는 진짜 화면처럼 행동해요.

- 화면 열기 → 로그인(서버가 "잠시 후"라고 하면 기다렸다 다시) → 내 정보 → 저장 불러오기 → `sync` 반복
- 서버가 정해 준 간격(`n`)을 지키고, 걸어 다니고, 1분에 한 번쯤 채팅하고, 바뀐 것이 있을 때 20~400 KB 저장을 올려요
- 다섯 명 중 한 명은 탭을 가려 둔 상태예요
- 방문자마다 자기 연결(브라우저 탭처럼 최대 2개)과 자기 인터넷 주소를 써요
- 정원이 차면 대기표를 받고 `api/queue.php` 만 부르며 기다려요

### 4.2 시험 환경 — 꼭 읽어 주세요

| 항목 | 시험 환경 | 실제 XAMPP PC |
|---|---|---|
| 운영체제 | 리눅스 (공유 시험 서버) | Windows 〔못 잼〕 |
| CPU | 4코어. **다른 작업이 동시에 3~3.8코어를 쓰고 있었어요** (부하 평균 10~39) | PC 마다 달라요 |
| 웹 서버 | Apache 2.4 prefork + mod_php, 일꾼 150개, KeepAliveTimeout 5 | Apache 2.4 (스레드 150개) + mod_php |
| PHP | 8.3 | 7.2 〔못 잼〕 — PHP 8 보다 느리다고 알려져 있지만 얼마나 느린지 직접 재지 못했어요. 문법은 PHP 7.2 로 검사했어요 |
| 데이터베이스 | MariaDB 10.11 (같은 서버) | MariaDB 10.3 |
| 방문자 | 같은 서버 안에서 만든 가상 방문자 (통신 지연 없음) | 실제 브라우저, 실제 회선 |
| HTTPS | 쓰지 않음 | 공개 서비스라면 사용 |

시험 서버를 다른 작업과 나눠 썼기 때문에 **응답 시간(p95 · p99)은 실제보다 나쁘게** 나왔어요. 반대로 통신 지연이 없어서 그만큼은 좋게 나왔어요.
믿을 만한 숫자는 **요청당 SQL 문 수, 주고받은 바이트 수, 요청당 CPU 사용 시간, 구조적인 한계(일꾼 수 · 정원 · 대기실 동작)** 예요. 아래 표에는 시험 때 다른 작업이 CPU 를 얼마나 쓰고 있었는지도 함께 적었어요.

### 4.5 로그인이 몰릴 때 〔잼〕

- 비밀번호 확인(argon2id) 한 번은 CPU 를 약 0.25초 써요. 4코어 서버가 1초에 처리할 수 있는 로그인은 다른 일을 안 해도 16번쯤이에요.
- 시험에서 1초에 20번까지 허용했더니(`login_per_sec = 20`) 서버가 로그인만 하다가 멈췄어요: 로그인 한 번에 서버 안에서만 8.8초, 연결 오류 192번.
- 기본값 `login_per_sec = 5` 에서는 넘치는 로그인이 "잠시 후 다시"(503 LOGIN_BUSY)를 받고 1~2초 뒤 스스로 다시 시도해요.
- 그런데 CPU 가 모자란 서버에서는 "1초에 5번 시작"만 막아서는 부족했어요. 끝나기 전에 계속 새로 시작해서 **동시에 120개**가 돌았고(하나에 메모리 64 MB), 로그인 하나가 24초 걸렸어요. 그 바람에 다른 요청까지 느려졌어요(방문자 200명에서 sync p95 794 ms, 저장 p95 4.9초). 7단계 코드도 똑같았어요(로그인 하나에 17초).
- 그래서 **동시에 돌아가는 비밀번호 확인 수**도 제한했어요: `login_concurrent = 4` (보통 코어 수만큼). 제한을 넣은 뒤 같은 서버에서 로그인 p50 이 0.4~0.9초로 돌아왔고 쌓이지 않았어요.
- 이 때문에 **한꺼번에 들어오는 속도는 1분에 150~300명**이 한계예요(기본값, CPU 에 따라). 1,000명이 동시에 "입장"을 누르면 다 들어오는 데 4~6분쯤 걸려요(시험에서는 약 6분). 기다리는 화면은 "지금 들어오려는 친구가 많아요"를 보여 주고 스스로 다시 시도해요.
- 코어가 많은 서버에서는 `login_concurrent` 를 코어 수로, `login_per_sec` 을 "코어 수 × 2" 정도로 올리면 돼요.

### 4.6 데이터베이스 질문 계획 (EXPLAIN) 〔잼〕

MariaDB 10.11 에 계정 30,000개를 넣고 자주 쓰는 질문을 확인했어요.

- 로그인, 계정 확인, 저장 읽기 · 쓰기, 텃밭, 채팅, 접속자, 차단 목록: 모두 색인(index)을 타고 0.15 ms 안에 끝나요.
- 전체를 훑는 질문은 **랭킹 3개뿐**이었어요: 상위 20명 30 ms, 활동 계정 수 129 ms, 내 순위 59 ms. 그래서 8단계에서 랭킹을 60초 동안 기억하게 했어요(내 저장과 상위 20명의 변화는 바로 반영).
- 더 줄이고 싶다면 `users(status)` 색인을 하나 추가하면 계정 수 세기가 빨라져요(선택 사항. 지금은 캐시로 충분해요).

## 5. 이 PC 한 대 (XAMPP) 로는 — 동시 접속 약 300명

**왜 300명인가**

- 〔잼〕 시험 서버(리눅스 · PHP 8.3 · opcache 켬 · Apache 일꾼 150개 · 파일 캐시 · MariaDB)는 CPU 를 1코어도 채 못 쓰는 상태에서 500명과 1,000명을 오류 없이 받았어요 (4.3).
- 〔못 잼〕 실제 XAMPP PC 는 Windows 에 PHP 7.2 예요. 이 조합은 직접 돌려 보지 못했어요. PHP 7.2 가 더 느리고 PC 가 다른 일도 한다는 점을 생각해서, 잰 값의 3분의 1 이하인 **300명**을 기본 정원(`max_online`)으로 잡았어요.
- 〔어림〕 **opcache 가 꺼져 있으면** 요청 하나의 CPU 가 11배라서(4.3 (다)), 4코어 PC 로는 100~150명 정도가 한계예요. opcache 를 켜지 못한다면 `max_online` 을 100 으로 낮추세요. 관리자 페이지의 점검 화면이 opcache 가 꺼져 있으면 알려 줘요.
- 300명이 넘게 오면 대기실이 받아 주므로, 정원을 낮게 잡아도 서버가 멈추지는 않아요.

### 5.1 확인할 설정 3가지

**① Apache 의 일꾼 수** — `C:\xampp\apache\conf\extra\httpd-mpm.conf`

```apache
<IfModule mpm_winnt_module>
    ThreadsPerChild        300
    MaxConnectionsPerChild   0
</IfModule>
```

- XAMPP 기본값은 보통 `ThreadsPerChild 150` 이에요. 300명을 받으려면 300 으로 올려 주세요. (8단계는 응답 뒤 연결을 닫으므로 150 으로도 대부분 충분하지만, 여유를 두는 편이 안전해요.)
- `httpd.conf` 에서 `Include conf/extra/httpd-mpm.conf` 줄 앞에 `#` 이 없어야 이 파일이 쓰여요.

**② PHP opcache 켜기** — `C:\xampp\php\php.ini`

```ini
zend_extension=opcache
opcache.enable=1
opcache.memory_consumption=128
opcache.validate_timestamps=1
opcache.revalidate_freq=2
```

- XAMPP 은 보통 opcache 가 꺼진 채로 설치돼요. 꺼져 있으면 요청마다 프로그램 파일을 다시 읽어서 CPU 를 훨씬 더 써요 (〔잼〕 보통 호출 하나에 1.5 ms → 16.3 ms, 11배).
- 바꾼 뒤 Apache 를 다시 시작하세요. 관리자 페이지의 "점검"에서 PHP 설정을 확인할 수 있어요.

**③ MariaDB 메모리** — `C:\xampp\mysql\bin\my.ini` 의 `[mysqld]` 아래

```ini
innodb_buffer_pool_size = 512M
max_connections = 350
```

- XAMPP 기본값(`innodb_buffer_pool_size=16M`)은 연습용이에요. PC 메모리의 4분의 1 정도(8 GB 라면 1~2 GB)까지 올려도 돼요.
- `max_connections` 는 Apache 일꾼 수보다 조금 크게 두세요.

### 5.2 체험관 쪽 설정 (`config/config.local.php`)

기본값 그대로면 300명 정원이에요. 바꾸고 싶을 때만 적으면 돼요.

```php
'capacity' => [
    'max_online'    => 300,   // 동시에 들어와 있을 수 있는 인원. 넘으면 대기실
    'target_rps'    => 150,   // 1초에 이만큼까지는 평소 속도. 넘으면 호출 간격을 늘려요
    'shed_rps'      => 400,   // 1초에 이만큼을 넘으면 새 방문자부터 "잠시 후 다시"
    'login_per_sec' => 5,     // 1초에 시작하는 로그인(비밀번호 확인) 수
    'login_concurrent' => 4,  // 동시에 돌아가는 비밀번호 확인 수 (보통 CPU 코어 수)
],
```

**정원을 정하는 법** 〔어림〕

1. `target_rps` = `코어 수 × 40` (opcache 를 켰을 때. 끄면 `코어 수 × 10`).
   - 〔잼〕 시험 서버에서 코어 하나가 초당 340~680번을 처리했어요(요청당 CPU 1.5~2.9 ms). 그 10분의 1 정도만 쓰도록 잡은 값이에요. PHP 7.2 가 더 느리고, PC 가 데이터베이스와 다른 일도 같이 하기 때문이에요.
2. `max_online` = `target_rps × 2` (한 사람이 평균 2초에 한 번 물어요).
3. `shed_rps` = `target_rps × 2.5`
4. `login_concurrent` = `코어 수`, `login_per_sec` = `코어 수 + 1`

예) 4코어 PC: `target_rps 150`, `max_online 300`, `shed_rps 400`, `login_per_sec 5`, `login_concurrent 4` — 기본값이에요.
예) 8코어 PC: `target_rps 320`, `max_online 640`, `shed_rps 800`, `login_per_sec 9`, `login_concurrent 8`.

정원을 넘겨 잡아도 서버가 바로 멈추지는 않아요. 초당 요청이 `target_rps` 를 넘으면 서버가 호출 간격을 늘려서 버텨요(시험에서 `target_rps 150` 으로 1,000명까지 받았어요). 다만 간격이 늘면 다른 사람의 움직임이 덜 자주 새로 그려져요.

- **부하 배수**가 계속 1.5 를 넘으면 사람이 정원에 비해 많은 거예요. `max_online` 을 줄이거나 6장으로 가세요.
- **줄이기**가 "1단계" 이상이면 서버가 새 방문자를 돌려보내는 중이에요.

### 5.4 하루 한 번 정리

```
php cli/tfm.php cleanup
```

오래된 세션 파일, 기한이 지난 캐시 파일을 지우고, 접속 위치를 데이터베이스에 옮겨 적어요. Windows 작업 스케줄러에 하루 한 번(새벽) 걸어 두세요. 걸어 두지 않아도 서버가 한 시간에 한 번씩 조금씩 정리해요.

## 6. 1,000명 준비

〔잼〕 시험 서버는 1,000명을 오류 없이 받았어요. 다만 CPU 를 1코어도 못 쓰는 상태라 서버가 호출 간격을 2배쯤 늘렸어요 (4.3 (나)).
〔어림〕 서버를 혼자 쓰는 4코어 PC(opcache 켬)라면 1,000명을 간격을 조금 늘린 채로, 8코어라면 평소 간격으로 받을 수 있어요: 1,000명 × 초당 0.47번 × 2.9 ms = 1.4코어.

순서대로 하세요.

1. **opcache 를 켜요** (5.1 ②). 이것 없이는 1,000명이 안 돼요.
2. **Apache 일꾼** — Windows XAMPP: `ThreadsPerChild 400`. 리눅스 Apache(prefork): `MaxRequestWorkers 200`, `ServerLimit 200`. `KeepAliveTimeout` 은 2~5 그대로 두세요 (체험관이 스스로 연결을 닫아요).
3. **MariaDB** — `innodb_buffer_pool_size = 1G` 이상, `max_connections = 500`.
4. **정원** (`config.local.php`):
   ```php
   'capacity' => [
       'max_online'       => 1000,
       'target_rps'       => 300,   // 4코어면 150 그대로 두어도 돼요 (간격을 늘려서 받아요)
       'shed_rps'         => 750,
       'login_per_sec'    => 9,     // 8코어 기준. 4코어면 5
       'login_concurrent' => 8,     // 코어 수
   ],
   ```
5. **들어오는 속도** — 기본 설정으로는 1분에 150~300명이 들어와요. 1,000명이 한꺼번에 오면 다 들어오는 데 4~6분 걸려요. 행사라면 입장 시간을 반별로 몇 분씩 나눠 주세요.
6. **회선** — 화면 파일이 한 사람당 1.8 MB(gzip)예요. 1,000명이 5분 사이에 들어오면 초당 6 MB(약 48 Mbit)를 **올려 보내야** 해요. 기관 회선의 올리기(업로드) 속도를 확인하세요. 모자라면 CDN 에 화면 파일을 맡기세요 (7.2). 들어온 뒤에는 한 사람이 1분에 20~45 KB 를 내려받아요: 1,000명이면 초당 0.3~0.8 MB.
7. **하루 한 번 `cleanup`**, 행사 중에는 `capacity` 로 부하 배수를 보세요. 계속 2 를 넘으면 정원이 서버에 비해 많은 거예요.

## 7. 10,000명 준비

1만 명은 **이 시험에서 실제로 돌려 보지 못했어요.** 아래는 잰 숫자로 계산한 준비 방법이에요 〔어림〕.

### 7.1 얼마나 필요한가 〔어림〕

| 항목 | 계산 | 값 |
|---|---|---:|
| 초당 요청 (평소 간격) | 10,000명 × 초당 0.47번 (1분에 28번 〔잼〕) | 약 4,700 |
| 초당 요청 (간격을 2배로 늘렸을 때) | 10,000명 × 초당 0.24번 (1분에 14번 〔잼〕) | 약 2,400 |
| PHP 에 필요한 CPU | 초당 요청 × 2.9 ms 〔잼〕 ÷ 사용률 60% | 평소 간격 약 23코어 · 늘린 간격 약 12코어 |
| 채널 | 10,000 ÷ 60 | 약 170개 |
| 저장 | 1분에 한 번 저장한다면 초당 167번 × SQL 10~20문 | 초당 SQL 1,700~3,400문 |
| 내려보내는 양 (들어온 뒤) | 10,000명 × 1분에 18~45 KB 〔잼〕 | 초당 3~7.5 MB (24~60 Mbit) |
| 화면 파일 (들어올 때) | 10,000명 × 1.3~1.8 MB | 13~18 GB — CDN 에 맡겨요 |
| 들어오는 속도 | `login_per_sec 32` (16코어 × 2) | 1분에 약 1,900명 → 다 들어오는 데 5~6분 이상 |
| 메모리 | php-fpm 64~128개 × 약 40 MB + 비밀번호 확인 16개 × 64 MB + APCu 0.5 GB + MariaDB 4~8 GB | 16~32 GB |

모든 값이 "PHP 8.3 · opcache 켬 · 이 시험 서버의 CPU" 기준이에요. 서버 CPU 가 다르면 달라져요. 그래서 **16코어 이상**을 권하고, 그 서버에서 직접 재 보기(9장)를 꼭 하라고 적었어요.

### 7.2 구성

```
방문자 ──https──> CDN ──> nginx ──> php-fpm (PHP 8.x + opcache + APCu) ──> MariaDB
                   │
                   └ index.html (압축본) 은 CDN 이 대신 보내 줘요
```

1. **리눅스 서버 한 대, 16코어 이상 · 메모리 32 GB 이상.** 지금 구조는 "웹 서버 한 대"를 전제로 해요 (7.4).
2. **nginx** — 열린 연결이 수만 개여도 일꾼을 붙잡지 않아요. `server/README-SERVER.md` 의 nginx 규칙(비공개 폴더 막기)을 꼭 넣으세요. nginx 는 `.htaccess` 를 읽지 않아요.
3. **php-fpm** — `pm = static`, `pm.max_children = 코어 수 × 4` 정도. `php.ini`: `opcache.enable=1`, `opcache.validate_timestamps=0`(파일을 바꾸면 php-fpm 을 다시 시작), `opcache.memory_consumption=256`.
4. **APCu** — `apt install php-apcu`, `apc.shm_size=512M`. 설치돼 있으면 체험관이 스스로 골라 써요 (`cache.driver = auto`). 파일 캐시보다 요청당 시간이 조금 줄어요 (〔잼〕 보통 호출 하나에 1.47 ms → 1.40 ms, 5% 정도).
5. **MariaDB** — `innodb_buffer_pool_size` 를 메모리의 4분의 1~절반, `max_connections` 를 `pm.max_children` 보다 크게. 보통 호출은 데이터베이스를 쓰지 않으므로, 데이터베이스는 저장 · 로그인 · 채팅 기록만 맡아요.
6. **CDN** — 화면 파일은 한 사람당 1.3~1.8 MB 예요. 1만 명이 10분 사이에 들어오면 그것만으로 초당 20~30 Mbit 이 필요해요. CDN 이 대신 보내게 하세요. API 주소(`/api/`)는 CDN 이 기억하면 안 돼요 (서버가 이미 `Cache-Control: no-store` 를 붙여요).
7. **`security.trusted_proxies`** — nginx · CDN 뒤에서는 **반드시** 설정하세요. 설정하지 않으면 서버가 모든 방문자를 "프록시 한 대"로 보고, 주소별 제한(로그인 시도 · 가입 · 차단)이 모든 사람에게 한꺼번에 걸려요. 값은 nginx · CDN 의 주소(또는 주소 범위)예요.
8. **정원** — `max_online 10000`, `target_rps` 는 7.1 의 계산값, `shed_rps` 는 그 2.5배, `login_per_sec` 는 `코어 수 × 2`.

### 7.3 미리 해 볼 것

- 9장의 방법으로 그 서버에서 직접 부하 시험을 돌려 보세요. 1,000명 → 3,000명 → 10,000명 순서로 올리면서 `capacity` 의 부하 배수와 응답 시간을 보세요.
- 행사 당일에는 입장 시간을 나눠 주세요. 기본 설정으로는 1분에 약 300명(`login_per_sec 5`), 16코어에서 `login_per_sec 32` 로 올려도 1분에 약 1,900명이 들어와요.

### 7.4 웹 서버를 여러 대로 늘리려면 — 아직 막고 있는 것

지금 구조로는 **웹 서버 한 대**까지가 안전해요. 여러 대로 나누려면 아래가 더 필요해요.

| 막는 것 | 지금 | 여러 대로 가려면 |
|---|---|---|
| 세션 | 서버의 `data/sessions` 폴더에 파일로 | 공유 저장소에 두거나, 같은 사람을 항상 같은 서버로 보내야(sticky) 해요 |
| 캐시 (채널 · 대기실 · 요청 한도) | 파일 또는 APCu — 서버마다 따로 | `cache.driver = db` (모든 서버가 `cache_kv` 표를 같이 써요). 다만 그러면 보통 호출도 데이터베이스를 쓰게 돼요. **이 조합으로 큰 부하를 재 보지는 못했어요** 〔못 잼〕. 본격적으로 하려면 Redis 같은 공유 메모리 캐시용 드라이버를 새로 만들어야 해요 |
| 업로드 사진 | 서버의 `uploads` 폴더 | 공유 저장소 |
| 정리 작업 (`cleanup`, 분양 자동 처리) | 한 서버의 작업 스케줄러 | 한 대에서만 돌리기 |
| 미리 압축한 화면 파일 | 서버마다 같은 빌드를 올리면 돼요 | (문제 없음) |

그래서 1만 명까지는 **서버를 여러 대로 나누기보다 한 대를 크게** 하는 쪽을 권해요.

## 8. 대기실은 이렇게 움직여요

1. 정원이 찬 뒤에 들어온 사람의 첫 `sync` 호출에 서버가 `503 QUEUE` 와 대기표(`t`), 앞에 선 사람 수(`pos`), 예상 시간(`eta`)을 줘요.
2. 화면은 "지금 마을에 친구들이 많아요 … 앞에 N명"을 보여 주고, 서버가 알려 준 간격(2~10초)으로 `api/queue.php?t=…` 만 불러요. 이 호출은 SQL 0문이고 1~2 ms 예요.
3. 자리가 나면 줄 맨 앞부터 차례가 와요. 차례가 된 사람의 화면이 스스로 다시 들어가요.
4. 탭을 닫으면 25초 뒤 줄에서 빠져요. 잠깐 통신이 끊겼다 돌아오면 원래 번호로 이어서 서요.
5. 들어와 있는 사람은 마지막 호출 뒤 3분(`seat_ttl 180`) 동안 자리를 지켜요. 로그아웃하면 바로 비워요.
6. 관리자는 항상 들어갈 수 있어요. 서버 PC 에서 직접 연 브라우저(localhost)는 줄이기 · 로그인 조절에 걸리지 않아요.

## 9. 직접 재 보기

**이 PC 가 지금 얼마나 바쁜지** — `php cli/tfm.php capacity` (5.3).

**부하 시험 도구** — 리눅스(또는 WSL)에서 Node.js 20 이상, PHP, Apache 가 있으면 돼요. 도구가 임시 폴더에 자기 서버와 자기 데이터베이스를 따로 띄워서 시험하고 끝나면 지워요. 운영 중인 서버의 데이터는 건드리지 않아요.

```bash
# 요청 한 번의 비용 (SQL 문 수 · 처리 시간)
node tools/loadtest.mjs --docroot dist/metaverse --probe

# 방문자 200명, 45초에 걸쳐 들어와서 60초 동안
node tools/loadtest.mjs --docroot dist/metaverse --users 200 --ramp 45 --duration 60 --workers 150 --keepalive 5

# MariaDB 로 (TFM_DB_HOST / TFM_DB_PORT / TFM_DB_USER / TFM_DB_PASS 환경 변수)
node tools/loadtest.mjs --docroot dist/metaverse --driver mysql --users 1000 --ramp 210 --duration 75

# 정원 100명에 200명이 올 때 대기실
node tools/loadtest.mjs --docroot dist/metaverse --users 200 --max-online 100 --stay 25,45 --duration 150
```

결과 읽는 법:

- `SQL per request` — 요청 하나에 평균 몇 번 데이터베이스에 물었나. 0.1~1 사이가 정상이에요.
- `ms of CPU per request` — 요청 하나에 서버 CPU 를 얼마나 썼나. 이 값으로 "코어 하나가 초당 몇 요청"을 계산해요 (1000 ÷ 값).
- `freed` — 응답 뒤 연결을 닫은 비율. `sync` 는 100% 여야 해요.
- `other processes on this machine` — 시험하는 동안 다른 작업이 쓴 CPU. 이 값이 크면 응답 시간은 믿지 마세요.
- `5xx / network errors` — 0 이어야 해요. 0 이 아니면 그 인원은 그 설정으로 감당하지 못한 거예요.

## 10. 문제가 생겼을 때

| 증상 | 볼 곳 | 조치 |
|---|---|---|
| 사람이 많지 않은데 접속이 안 되거나 한참 걸려요 | Apache 일꾼 수(`ThreadsPerChild`), `capacity.close_after_ms` 가 0 인지 | 5.1 ① 처럼 일꾼을 늘리고, `close_after_ms` 를 1000 으로 |
| "지금 들어오려는 친구가 많아요"가 자주 떠요 | `capacity` 의 로그인 줄 | 정상이에요(로그인 조절). 코어가 남으면 `login_concurrent` 와 `login_per_sec` 을 올리세요 |
| 모든 것이 느려요 (사람이 적어도) | 관리자 점검 화면의 "수용 인원 · 부하" 줄에 opcache 가 "꺼짐"인지 | `php.ini` 에서 opcache 를 켜고 Apache 를 다시 시작 (5.1 ②) |
| "지금 마을에 친구들이 많아요 … 앞에 N명" | `capacity` 의 마을 안 · 대기실 | 정상이에요(정원). 서버에 여유가 있으면 `max_online` 을 올리세요 |
| 다른 사람의 움직임이 뚝뚝 끊겨 보여요 | `capacity` 의 부하 배수 | 1.5 를 넘으면 서버가 간격을 늘리고 있는 거예요. 정원을 줄이거나 opcache · 코어를 늘리세요 |
| `capacity` 의 숫자가 전부 0 이에요 | 캐시 방식이 `apcu` 인지 | 관리자 페이지의 점검 화면에서 보세요 |
| 캐시 방식이 `off` 로 나와요 | `data/cache` 폴더에 쓸 수 있는지 | 폴더 권한을 확인하세요. `off` 면 7단계 방식(전부 데이터베이스)으로 동작해요 |
| 화면이 옛 내용으로 떠요 | `index.html` 을 손으로 바꿨는지 | `index.gz.html` · `index.br.html` 을 지우거나 다시 빌드 |
| 정지한 계정이 랭킹에 남아 있어요 | — | 정지하는 순간 랭킹 캐시를 지우므로 바로 사라져요. 남아 있다면 `php cli/tfm.php cache:purge` |

## 11. 설정 이름 모음 (`config/config.php` — 바꿀 때는 `config.local.php` 에)

| 설정 | 기본값 | 뜻 |
|---|---:|---|
| `cache.driver` | `auto` | `auto`(APCu 가 있으면 메모리, 없으면 파일) · `apcu` · `file` · `db` · `off` |
| `cache.user_ttl` | 15 | 계정 정보를 기억하는 시간(초). 계정이 바뀌면 바로 지워요 |
| `cache.block_ttl` | 15 | 차단 목록을 기억하는 시간(초). 새로 차단하면 바로 지워요 |
| `cache.settings_ttl` | 30 | 관리자 설정을 기억하는 시간(초) |
| `cache.ranking_ttl` | 60 | 랭킹을 기억하는 시간(초) |
| `capacity.max_online` | 300 | 정원. 넘으면 대기실. 0 = 제한 없음 |
| `capacity.target_rps` | 150 | 이 초당 요청 수까지는 평소 간격 |
| `capacity.shed_rps` | 400 | 이 초당 요청 수를 넘으면 새 방문자부터 돌려보내요. 0 = 끄기 |
| `capacity.login_per_sec` | 5 | 1초에 시작하는 로그인(비밀번호 확인) 수 |
| `capacity.login_concurrent` | 4 | 동시에 돌아가는 비밀번호 확인 수 (보통 CPU 코어 수) |
| `capacity.seat_ttl` | 180 | 마지막 호출 뒤 자리를 지켜 주는 시간(초) |
| `capacity.close_after_ms` | 1000 | 다음 호출이 이 시간 이상 뒤이면 응답 뒤 연결을 닫아요 |
| `capacity.gzip_json` | 켬 | 큰 응답(sync · 저장 불러오기 · 채팅 목록 · 랭킹)을 줄여 보내요 |
| `channels.size` / `channels.hard` | 60 / 90 | 한 채널의 기준 인원 / 최대 인원 |
| `sync.min_ms` … `sync.hidden_ms` | 1000 … 20000 | 다음 호출까지의 간격(상황별) |
| `sync.aoi_radius` / `sync.max_near` | 90 / 40 | 이 거리(m) 안, 이 인원까지만 보내요 |
| `sync.save_every` | 60 | 저장 권장 간격(초) |
| `sync.enabled` | 켬 | 끄면 7단계 방식(따로따로 묻기)으로 돌아가요 |
| `db.mysql.persistent` | 끔 | 데이터베이스 연결을 재사용해요 (php-fpm 에서 권장) |

환경 변수로도 줄 수 있어요: `TFM_CACHE_DRIVER`, `TFM_MAX_ONLINE`, `TFM_TARGET_RPS`, `TFM_SHED_RPS`, `TFM_LOGIN_PER_SEC`, `TFM_LOGIN_CONCURRENT`, `TFM_SEAT_TTL`, `TFM_CLOSE_AFTER_MS`, `TFM_CHANNEL_SIZE`, `TFM_CHANNEL_HARD`, `TFM_SYNC`, `TFM_DB_PERSISTENT`.
